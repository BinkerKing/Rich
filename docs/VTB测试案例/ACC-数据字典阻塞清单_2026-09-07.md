# ACC CA / ACC CB 数据字典阻塞清单

## 已核实的一代链路

SAFE1.3 `BaseAccDataExtractServiceImpl` 先调用 `extract_ACCCA` / `extract_ACCCB`，将结果承载为 `BaseAif` 与 `BalTab`；之后写入账户和收支余业务实体，并保留未审核重跑、已审核已报送不覆盖、关户、新增、客户变更等状态分支。`BaseAif` 的实际字段包括 `stacod`、`lmtbal`、`apvno`、`lmttp` 和 `actp`；其中 `actp` 还需经 `AccountTypeMapping` 转换为 SAFE 账户性质。

## 当前字典状态与可复现差异

当前 VTB 贴源 `AifTab` 只有 13 个字段：账号、币种、客户号、账户类型、开/销户日期、限额等简化字段，没有 `BaseAif.stacod`、`lmtbal`、`apvno`、`lmttp`，也没有 `AccountTypeMapping` 对象。

因此，现有 ACC CA Mapping 中的账户性质、账户限额、批件号、限额类型和“标准账号优先”无法等价实现；当前 SQL 验证通过仅表示 SQL 可执行，不能证明与一代结果一致。ACC CB 又依赖已加工的 Account 生命周期结果，不能用简单的 `BlnTab + AifTab` 连接替代。

## 已完成的检查

- ACC CA 与 ACC CB 的数据字典界面/API Mapping 可读取，SQL 语法验证均通过。
- ACC CA 实体 `vtb.t_safe_accca` 已存在且结构一致。
- 未创建或运行生成过程：在上游字段与生命周期尚未建模时生成过程会产出不等价结果，不满足本任务四项门槛。

## 需要先补齐的最小对象

1. 将一代 `extract_ACCCA` 的输出契约建为可追溯来源（至少补 `stacod`、`lmtbal`、`apvno`、`lmttp`、`actp` 及业务日/分行字段）。
2. 建立 `AccountTypeMapping` 的 `bankAccountType -> safeAccountType` 映射来源。
3. 将 Account 的“未审核覆盖、已审核已发送保护、关户/客户变更新增”作为可表达的 UPSERT/状态规则后，方可生成 ACC CA；ACC CB 必须以该 Account 结果为输入。

证据：`BaseAccDataExtractServiceImpl.java:99-108,192-404`，`BaseAif.java`，`AccountTypeMapping.java`。
