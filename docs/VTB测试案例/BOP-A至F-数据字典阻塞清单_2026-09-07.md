# BOP A–F 数据字典阻塞清单

## 一代真实链路

SAFE1.3 先把交易加工到 `BopTransaction` 数据池；`BopTransServiceImpl.trans(bopTransaction, targetType)` 由人工选择 `BOPA` 至 `BOPF`，校验收支方向后写入相应正式表。`bopType` 即已选的目标报表类型，空值表示仍留在数据池，不应自动生成任何 BOP A–F 记录。

一代的正式表提取服务（`Bopa/Bopb/Bopc/Bopd/Bope/BopfMetroExtractServiceImpl`）则以已形成的 `BopTab.DataType` 为来源，按 `dealNo` 更新未审核记录，审核记录跳过。

## 当前字典结论

- `T_SAFE_BOPA` 至 `T_SAFE_BOPF` 当前均为 0 个 Mapping 规则、0 个临时表/场景，尚未建立可执行来源。
- 现有二代 `BopTransaction` 贴源表只有 `CNUM`，不含一代转换时所用的 `Customer.safeCusType` / `bopCusTypeByIntesa`；因此客户类型 C/D/F 不能可靠从现有字段推断。
- 一代转换还依赖 Account NRA 判断，并包含已选类型、未审核/已审核、目标类型收支方向等生命周期状态。这些不是“业务区分未定”可以被常量替代的字段逻辑。

## 与当前业务决定的关系

根据当前决定，BOP 的最终业务区分保持空。与一代一致的处理是保留 `bopType` 为空、A–F 输出为空；不能以未分流的 `BopTransaction` 作为六张正式表的共同输入。

要进入四项验证，最小前置是：建立可审计的“人工分流目标类型”输入，以及一代所需的客户 SAFE/BOP 类型和 NRA 账户来源；然后分别为 A–F 配置 BopTab 到报表字段映射和未审核更新/审核跳过生命周期。

证据：`BopTransServiceImpl.java:146-204,221-360`；`BopTab.hbm.xml`；`Bopa/Bopb/Bopc/Bopd/Bope/BopfMetroExtractServiceImpl.java`。
