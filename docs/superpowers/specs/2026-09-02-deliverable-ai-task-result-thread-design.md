# 交付物 AI 任务结果线程设计

## 目标

让交付物中的 AI 任务在完成后给出清晰、可追溯的结果回复。原始任务与交付物要求保持不变；AI 的结论作为该任务的子记录呈现。较长结论归档为交付物目录内的 Markdown 文件，并从回复中链接。

## 已确认的交互

交付物要求记录按时间显示。`AI 任务` 记录是一次委托的父项，展示执行器、任务状态和完成时间。成功完成后，系统自动在其下写入一条 `AI 回复` 子项：

- 显示简短结果总结、执行器与回写时间；
- 状态固定为“待复核”，明确该结果尚未成为人工确认的结论；
- 显示证据或相关材料链接；
- 当存在归档报告时，显示“查看完整报告.md”链接；
- 原始 AI 任务文字、既有需求与材料记录不会被改写。

UI 采用任务线程而不是平铺独立记录，以保持任务与结果的一一对应。子项需在窄窗口下与父项同列换行，不能再挤压状态文字。

## 数据模型

新增记录类型 `ai_task_result`，并新增可选字段：

```ts
type DeliverableRecord = {
  // existing fields
  parentRecordId?: string; // 仅 ai_task_result 使用，指向 ai_task 记录
  aiTaskResult?: {
    taskId: string;
    status: "needs_human" | "approved" | "rejected";
    executor: "hermes" | "multica";
    completedAt: string;
    report?: DeliverableRecordAttachment;
    evidence: DeliverableRecordAttachment[];
  };
};
```

`ai_task` 继续使用既有 `aiTask` 字段。发起任务时，前端先生成 AI 任务记录 ID，再将该 ID 作为 `originRecordId` 写入任务请求；这样后端回写时可精确定位父项，不依赖标题或时间猜测。

兼容性：缺少上述字段的旧记录按当前方式显示。不存在子结果时，旧 AI 任务没有视觉或数据变化。

## 完成与回写流程

1. 用户从交付物界面发起任务。前端先创建状态为 `publishing` 的 `ai_task` 父记录，并将它的 ID 同任务请求一起持久化。
2. 后端创建任务后、开始执行前，以 `originRecordId` 将该父记录绑定到真实任务 ID 与排队状态；该绑定避免任务完成与前端二次保存发生竞争。
3. Hermes 或 Multica 使用 `rich_task_report_result` 上报 `summary`、`evidence`，并可选上报 `reportMarkdown`。
4. 后端先把任务转换为 `succeeded / needs_human`，再以 `originRecordId` 定位对应交付物。
5. 后端创建或更新唯一的 `ai_task_result` 子记录；同一任务重复上报不得产生重复子项。
6. 若 `reportMarkdown` 非空，后端在该交付物实际目录创建 `AI任务结果/` 并写入报告；子记录保存文件名、相对路径和大小。文件名格式为 `YYYYMMDD-<安全任务标题>-<任务短 ID>.md`。
7. 前端刷新或重新打开交付物时，按 `parentRecordId` 将子记录紧跟在其父任务下渲染。

任务服务仍是执行过程与审计的唯一来源；交付物记录是面向用户的、可追溯的结果投影。

## 报告策略

- `summary` 是必填的简短结论，最多 2,000 字符；它始终直接展示在回复中。
- `reportMarkdown` 是可选的详细报告，最大 100,000 字符。存在时始终归档为 Markdown，而不是塞进记录正文。
- Agent 提示词要求：有多项发现、逐项证据、表格、长解释或完整分析过程时提供 `reportMarkdown`；简单结论只上报 `summary`。
- 报告路径只能由服务端基于交付物目录生成。Agent 不能提供文件系统目标路径，避免越界写入。
- 归档失败时，任务结果仍完成并保留总结；子记录显示“结果归档失败”，且服务端保留可重试的报告内容或明确失败原因。不得因为写文件失败重复创建结果子项。

## 权限与安全边界

- 仅允许当前运行中的 `deliverable_analysis` 任务调用结果回写工具。
- 后端只更新任务请求所绑定的 `projectId`、`deliverableId` 与 `originRecordId`；找不到父记录时返回可诊断错误，不能猜测其它记录。
- Markdown 写入路径经过目录约束和文件名清洗，且只能落在交付物目录的 `AI任务结果/` 下。
- 自动回写只新增 AI 结果记录，不自动修改需求、状态、版本、业务数据或原始材料。

## 展示状态

| 任务状态 | 父 AI 任务 | 结果子项 |
| --- | --- | --- |
| queued / running | 显示排队或执行中 | 无 |
| succeeded + needs_human | 显示已完成、待复核 | 自动显示总结与报告链接（如有） |
| failed / cancelled | 显示失败或已取消 | 无；继续显示任务中心的失败原因 |
| 归档失败 | 显示已完成、待复核 | 显示总结与“结果归档失败，可重试” |

本期不实现人工“批准/驳回”按钮；`needs_human` 只是为后续审核流程保留的状态，避免把 AI 结果误当最终交付结论。

## 验收与测试

- 前端模型能解析和序列化 `ai_task_result`、父子关系、报告与证据附件。
- 发起任务的请求包含与父 AI 任务记录一致的 `originRecordId`。
- `rich_task_report_result` 对带详细报告的成功任务：更新任务状态、生成报告文件、创建一条子记录。
- 同一任务重复上报时：更新既有子记录，不生成重复记录或重复报告链接。
- 无详细报告时：创建只含摘要的子记录，不创建空 Markdown 文件。
- 报告文件必须位于目标交付物的 `AI任务结果/` 下；任何越界标题和路径输入都不能逃逸目录。
- UI 在父项下显示结果、待复核状态及 Markdown 链接；长文本不撑坏现有记录布局。
- 后端归档失败时，任务成功结果与摘要仍可见，且错误状态可供重试。

## 非目标

- 不自动把 AI 结论并入“交付物要求”或业务数据。
- 不实现报告编辑器、人工审核动作、通知中心或跨交付物结果复用。
- 不改变现有非 AI 记录、版本控制和文件管理的行为。
