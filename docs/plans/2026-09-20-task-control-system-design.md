# 任务控制系统设计

## 目标与边界

任务系统是项目中唯一管理任务、计划、执行反馈和验收的地方。项目模块（交付物、测试中心、数据字典等）只保存并展示各自的专业数据；它们不展示任务、步骤或任务来源。

用户先在 Codex 对话中澄清需求，再创建任务并进入工作台。工作台绑定该对话；对话和任务文档共同形成持续更新的上下文。Codex 依据当前计划调用 MCP 修改项目模块，任务系统记录由此产生的执行回执和验收证据。

## 核心模型

### 任务

任务描述一个最终业务目标，保存任务文档、验收标准、当前状态、绑定对话、当前计划版本和最终结论。任务不是模块任务的聚合，也不将步骤同步到模块页面。

任务状态为：`draft`、`clarifying`、`executing`、`blocked`、`review`、`completed`、`cancelled`。任务是否完成由必需步骤与任务级验收规则决定，不能仅由 Codex 的自然语言结论决定。

### 步骤树

计划是一棵由步骤组成的树。父步骤代表阶段或可汇总目标；叶步骤通常承担具体执行。每个步骤可有：

- `parentId` 和排序位置，形成层级计划；
- 标题、目标、优先级、依赖步骤；
- 输入引用、预期产出、验收规则和建议 MCP 参考；
- 当前状态、执行反馈、MCP 执行回执和证据引用；
- 创建/修改时间与计划版本信息。

步骤是任务系统的最小反馈和验收单元。一个步骤可以连续调用多个 MCP 工具，但应只对应一个能独立验收的结果。例如，形成 Mapping 可读取字典、写入文件并运行覆盖校验；以 Mapping 创建测试案例则是后续独立步骤，因为其验收结果不同。

## 动态计划与不可变历史

计划永远表示“当前最佳计划”，不是在任务创建时冻结的最终蓝图。用户与 Codex 可在持续对话中新增、细化、调整优先级或重排尚未开始的步骤；Codex 也可根据实际 MCP 结果自行提出和执行合理调整。

步骤一旦进入 `running`、`completed`、`failed`、`blocked` 或 `skipped`，其结构性信息不可删除或篡改。对已执行步骤的需求变化应通过新增承接步骤表达。已经完成但后续证明无效、不再采用的步骤保留原始执行与证据，状态标记为 `superseded`，并记录替代步骤及废弃原因；不能删除。

建议状态为：

```text
planned -> ready -> running -> feedback -> review -> completed
                    |           |         |
                    +-> blocked +-> failed +-> superseded
                    +-> skipped
```

父步骤根据子步骤状态、优先级和依赖聚合进度，不直接覆盖子步骤的结论。

## Codex 与 MCP

步骤中的 MCP 工具仅是建议参考，不是权限白名单。Codex 可基于整个任务、对话与项目上下文自行选择任意已授权 MCP 能力，读取其他模块、采取替代路径、调用多个工具，或提出计划调整。

真正的权限边界由全局 MCP 工具的读写安全策略定义。任务系统负责保存每个实际行动的执行回执：工具名、输入摘要、输出对象/文件引用、写后验证、失败或风险说明，以及它对应的步骤。模块无需保存该回执，也无需知道任务树存在。

## 迁移任务示例

```text
数据迁移
├─ 迁移设计（P0）
│  ├─ 梳理源目标字段与范围（P0）
│  ├─ 形成字段 Mapping（P0）
│  └─ 生成迁移脚本（P0）
└─ 迁移验证（P1）
   ├─ 校验 Mapping 与脚本一致性（P1）
   ├─ 创建迁移测试案例（P1）
   ├─ 执行迁移验证（P1）
   └─ 汇总差异和验收结论（P1）
```

交付物模块最终只显示 Mapping、SQL、说明文档和版本；测试中心只显示测试案例、运行、证据和缺陷。工作台才显示完整任务树、每一步的反馈以及最终任务结论。

## 关键决策（ADR）

**决策：模块不实现任务模式。** 通过 MCP 对模块执行读写，避免在任务系统与专业模块之间维护重复任务状态。代价是任务工作台必须可靠保存通用对象引用和回执。

**决策：步骤树是计划和执行的唯一核心。** 计划可动态修改以适应对话中的新信息；已执行步骤不可删除，使用 `superseded`、`skipped` 等状态保留历史。代价是树会逐渐积累历史节点，需要工作台提供“仅显示当前有效计划”的视图。

**决策：建议工具而非工具白名单。** Codex 保留自主理解和解决问题的能力；全局 MCP 安全机制承担权限控制。代价是执行回执必须足够完整，以便用户审阅超出初始建议的行动。

## 验收与失败处理

每个必需叶步骤必须具备验收规则和至少一条证据或有效的跳过/废弃理由。任务进入 `review` 前，所有必需步骤必须 `completed` 或被明确 `skipped`/`superseded` 并由替代步骤满足原验收意图。MCP 失败不会删除或伪造执行结果：步骤保持 `blocked` 或 `failed`，Codex 可重试、使用替代工具，或新增承接步骤。
