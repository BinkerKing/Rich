# 任务工作台使用与写回

## 开始一个任务

在 Rich 的 Codex 对话中选择「任务模式（自动适配）」并描述需求。也可以从任务工作台的「在 Codex 中发起任务」打开新对话，再选择任务模式。Codex 先理解需求，选择已有专用承接或创建通用任务；不要求一开始就明确全部细节。

需求和计划可以在对话中确认，也可以在工作台点击确认。工作台展示需求、可展开的计划、步骤记录、材料和成果；细化、优化、执行按钮将指令发送到绑定的同一个 Codex 对话。需要补充说明时点击「打开绑定对话」。

按钮指令仅携带任务 ID、发起版本、操作范围和本次要求，连续播放及最终核验同样使用简短指令，不重复附加任务模式说明或完整 PRD。Codex 沿用绑定对话，并通过 `rich_workbench_manage get` 读取最新任务状态，写回使用最新版本；工作台中的修改不能只依赖对话记忆。

「对话回合已结束」只表示 Codex 本次返回；步骤完成必须有依据，任务完成还需要已确认的计划、全部步骤完成或跳过，以及最终产物。修改需求或计划结构后，需要重新确认相应内容。历史版本可查看，不提供自动回滚。

## MCP

工具 `rich_workbench_manage` 提供 `list/get/history/create/update/plan/step/record/resource/confirm`。所有任务修改需要 `taskId` 与 `expectedVersion`，冲突后重新读取、评估再修改。`conversationId` 是 Rich 对话记录 ID，不是 Codex 原生 thread ID；任务模式启动提示中会提供。

创建示例（替换对话 ID）：

```json
{
  "action": "create",
  "context": { "requestId": "unique-create-request" },
  "input": {
    "title": "分析 Mapping 材料",
    "conversationId": "rich-conversation-record-id",
    "requirement": "结合材料与代码整理字段来源，列出待确认差异",
    "acceptance": "结论附材料依据，冲突单列",
    "outputTarget": "字段分析报告"
  }
}
```

每次新的写入使用新的 `context.requestId`；相同请求重试复用原 ID。根据返回的最新版本写入步骤：

```json
{
  "action": "step",
  "taskId": "work-task-id",
  "expectedVersion": 5,
  "context": { "requestId": "unique-step-request" },
  "input": { "id": "s1", "status": "done", "evidence": "已核对材料清单，见登记的分析报告" }
}
```

`confirm` 仅在用户明确确认后调用，`input` 为 `{"target":"requirement或plan","evidence":"用户确认内容"}`。计划修改必须保留已有步骤与状态；取消步骤使用 `skipped` 并写明原因。材料与成果通过 `resource` 登记，可关联 `stepId`。`format` 为 `file/link/information`：文件或链接填 `location`（真实绝对文件路径、file URL、网页或 SVN 地址），信息可只填 `content`（例如数据库主机、端口、库名及凭据存放位置）。保留文件原位置，不要求再次上传。工作台支持上传文件、展开信息、复制地址或内容；本地引用经 Rich 桌面打开原文件或目录，网页链接跳转浏览器，未关联打开程序的地址可复制使用。

## CLI

在仓库目录执行，默认连接 `http://127.0.0.1:31515`，可通过 `RICH_API_URL` 指向实际 Rich 服务地址：

```sh
node scripts/rich-cli.mjs workbench list
node scripts/rich-cli.mjs workbench get <taskId>
node scripts/rich-cli.mjs workbench create --file task.json
node scripts/rich-cli.mjs workbench plan <taskId> --file plan.json
node scripts/rich-cli.mjs workbench record <taskId> --file record.json
node scripts/rich-cli.mjs workbench history <taskId>
```

创建文件包含上面示例的 `input` 内容；修改文件格式为 `{"expectedVersion":最新版本,"input":{...}}`。REST 和 CLI 共用业务规则及版本校验；需要请求级幂等写入时使用 MCP 的 `context.requestId`。

## 首版边界

- 「任务工作台」与「应用开发」是应用中心中的两个独立应用；原应用开发数据与功能保留。⌘7 继续打开任务工作台。
- 首版提供通用任务闭环，保留交付物分析模式；Mapping 专用识别、批量数据字典同步和同步结果核验留待下一阶段。
- 对话绑定失效时可通过 `update.input.conversationId` 改绑有效 Rich 对话；有执行中的指令时禁止改绑或归档。
- 重启后本机未完成指令标记为结果待核实，不自动重发，避免重复执行。
- 已测试 SQLite 与模拟 Codex 的持久化、API、MCP 和 UI；真实 Codex 的完整业务交付以及 PostgreSQL 实库尚需后续验收。

## 步骤确认项

每个步骤有确认项区域。点击「梳理确认项」让绑定 Codex 整理具体前置条件或执行中阻塞：有选项则选择，信息不足则填写文字，并点击确认保存。没有列出确认项的步骤不能直接执行。必填项必须满足放行条件；例如「环境未就绪」仍阻止执行。父步骤的未满足条件对子步骤生效。

MCP/CLI 增加 `checkpoint` 与 `answer`，同样要求最新 `expectedVersion`。checkpoint 的 input 为 `{id,stepId,title,description?,phase:"before"|"during",required:true,options:[{value,label,allowsExecution}]}`；options 为空使用文本输入。answer 的 input 为 `{id,answer}`，只能记录用户明确的答复。条目定义变化清除原答复；已满足条件的答案变更会重新核对相关步骤、使计划需再次确认。历史保留答复记录。

确认答案不会自动启动执行，也不能取消已经发出的外部操作；后续步骤和状态写回会重新校验。整个任务或父步骤批量执行前，所选范围的确认项需全部满足；也可以先确认并单独执行已经具备条件的步骤。

## 播放与执行跟随

顶部播放键按计划顺序逐步推进；先确认当前需求和计划。每一步开始前检查自身及上级确认项，没有确认项时先让 Codex 梳理并停下等待用户；未满足条件不执行。当前步骤实际写回完成后才进入下一步，失败或没有完成依据就停止。全部步骤完成后再由 Codex 核验最终交付，不能以回合结束替代交付完成。

右侧默认「步骤记录」，展示实际工具活动、Codex 返回的进展和步骤写回；「材料与成果」保留引用清单。运行时页面跟随当前执行步骤，自动展开其父级并定位；停止时保留最后步骤。日志每次指令保留最近 300 条，流式文字定期保存（每段最多 6000 字），完整交流仍在绑定对话。服务重启不自动重放。

### 需求变更记录

需求总览的“请 Codex 细化需求”和“确认当前理解”位于模块右上角。需求版本以用户确认作为节点：首次确认生成需求 v1；确认前的草稿修改不产生需求版本。已确认需求调整后回到待确认状态，再次确认生成 v2，以此类推；重复确认已确认内容不生成新版本。

“变更记录”按确认时间倒序展示已确认版本，展开比较相邻确认版本的需求标题、当前理解、完成条件、尚待明确和交付目标。调整中的草稿不覆盖已有确认版本。记录由历史快照中的需求确认状态转换提取，不受普通任务修订最近 100 条展示限制。任务修订编号仅用于内部写回追踪，与需求版本分别计数。


### 完整 PRD 与动态计划

需求通过 `prd` 保存完整 Markdown 文档并以富文本阅读，`requirementChangeSummary` 说明本次改动。历史页每个确认版本展示完整 PRD 与改动说明，不再按字段展示卡片。旧数据按现有目标、验收、交付和待明确内容组成文档，不补造事实。已有 PRD 时，更新旧需求字段必须一并提交完整正文，避免两份信息不一致。

确认项的新答复自动补入 PRD 的“执行中明确的信息”章节，保留原有正文，需求与计划进入待确认。Codex 后续梳理时需将补充信息整合至对应章节并清理已解决的待明确事项。再次确认才生成下一需求版本。

未执行步骤可调整目标、内容和顺序；调整后计划须重新确认。已开始执行的步骤锁定计划内容、位置与父子关系，允许写入执行进展与结果，但不能重写历史目标或重置为未执行。变更通过新增后续步骤承接；已存在步骤仍保留，取消的步骤注明原因后跳过。

### 执行记录与确认项写回

步骤记录按时间倒序显示，内部 `rich_workbench_manage` 开始/结束活动不再逐条展示。日志中的步骤标题和待确认提示可直接定位到步骤确认表单。重新打开任务时恢复最后执行步骤。

业务写回遇到修订变化时，对照读取版本与当前业务内容：仅执行指令/日志发生变化可安全重试；需求、计划、答复等业务内容变化仍报冲突。梳理确认项后读取实际保存结果，无确认项时报告写回失败，不再误提示用户填写不存在的表单。

父步骤确认区域汇总展示子步骤确认项并注明所属步骤；确认项准备结果按整个指定步骤范围核验。纯分组父步骤复用子步骤确认项，不要求重复的问题；父步骤自己登记的必填条件仍对所有子步骤生效。


确认项无论是否提供预设选项，均支持自行填写。带选项的表单可切换“选择选项 / 自行填写”，答案以 `answerMode: option|text` 保存，旧接口默认按已有选项校验。自由文本作为用户的实际答复写入 PRD，仍需复核并确认更新后的需求与计划。预设的否定选项仍保持阻塞。确认项标题、输入字号为 16px，说明为 15px，并提高对比度。


### 信息补充与需求变动（2026-09-06 修正）

仅补充缺失资料无需再次确认需求或计划：首次填写确认项自动并入当前 PRD，保持已有确认状态，不新增需求版本。工具更新完整 PRD 可指定 `requirementUpdateKind: supplement`；目标、范围、验收等既有要求发生变动必须使用 `change`（默认），需要再次确认。修改已有确认答案按变动处理。首次确认前的补充不会自动确认需求。

Codex 应检查答复与已确认要求是否矛盾，不能将取消测试等范围调整当作普通补充。当前确认版本可随资料补充完善；进入下一版变更后，前版内容保持不变。任务修订仍保存每次写入的原始快照。
