# 项目管理数据字典 Mapping 规则手册

这份手册写给 Hermes、Codex、Mac Mini Agent 和后续维护 Rich 的开发者。它记录项目管理中「数据字典 / Mapping」的固定模版规则。

本手册是持续演进文档。用户后续提出新的 Mapping 展示、编辑、检索、生成代码要求时，先补充这里，再决定是否固化到数据库 schema、UI 约束、CLI 或 Hermes 工具说明中。

## 模板治理与强制执行

本手册描述规则；Rich 中的「数据字典模板版本库」保存可执行的规则版本。两者必须同步维护，不能只改其中一处。

### 1. 模板版本状态

| 状态 | 是否可用于录入 | 含义 |
| --- | --- | --- |
| `draft` | 否 | 正在讨论或整理的规则草案，不得作为 AI 或人工录入依据 |
| `review` | 否 | 等待确认的候选版本，可评审、不可用于正式数据 |
| `published` | 是 | 当前唯一允许用于新增、修改、导入和 AI 生成的版本 |
| `superseded` | 否 | 被新发布版本替代，只保留历史追溯 |
| `retired` | 否 | 明确废止，不再使用 |

每次只允许一个全局 `published` 模板版本。项目可以在规则版本中声明少量项目级补充，但不得覆盖全局硬性规则。

### 2. 规则项结构

每条规则项必须包含：`元类型`、`属性`、`是否必填`、`数据类型`、`允许值/格式`、`填写说明`、`禁止写法`、`示例`、`规则状态`。没有这些信息的要求只算讨论，不算可执行模板。

### 3. 变更流程

1. 用户提出新要求时，先创建变更记录，写清楚原因、影响的元类型和属性。
2. 在 `draft` 版本中修改规则项，不能直接修改已发布版本。
3. 评审后将候选版本标为 `review`；确认后发布为新的 `published` 版本，并将上一版改为 `superseded`。
4. 发布后，AI/CLI/导入程序以新版本校验新增或修改数据。
5. 历史数据不自动篡改；由变更记录列出需要补齐或迁移的数据，并单独执行整改。

### 4. 强制录入原则

1. Agent 在写入库元、表元、字段元、码值元、场景元、Mapping 元、涉及字段元或动作元前，必须读取当前 `published` 模板版本。
2. 必填属性缺失、固定码值不合法、类型格式不合规时，必须拒绝写入并返回缺失项；不得自行填默认业务含义。
3. 证据不足的数据允许写入 `待确认`，但必须写清证据缺口和待确认项，不能伪造完成态。
4. 不允许以备注替代必填属性；不允许以自由文本替代固定码值、结构化关联或动作链。
5. 模板没有定义的属性或枚举值，不得由 Agent 擅自新增；必须先走模板变更流程。

### 5. 整改闭环与模板优化

数据字典界面中的整改不是一次性批注，而是模板治理的反馈入口。整改记录必须绑定到明确的 `元类型 + 元 ID + 属性名`，并保存整改要求、状态、修复说明、创建和修复时间。

| 整改状态 | 含义 | 界面标识 |
| --- | --- | --- |
| `open` | 待整改，尚未完成修复 | 红色边框 |
| `fixed` | 已按要求修复，等待人工或 AI 复核 | 琥珀色边框 |
| `verified` | 修复经复核通过 | 绿色边框 |
| `cancelled` | 取消整改，保留审计原因 | 不再作为活动标识 |

整改完成后，系统和 AI 应按元类型、属性、整改关键词、重复频次和修复说明汇总分析：

1. 单个数据问题：修复对应元属性，状态从 `open` 进入 `fixed`，复核后进入 `verified`。
2. 同一属性反复出现同类整改：创建模板变更记录，提出必填、枚举、格式、校验或填写说明的改进建议。
3. 模板变更经确认后，发布新的 `published` 版本；新版本必须引用对应整改证据，并列出历史数据迁移/复核范围。
4. AI 不得根据一条整改擅自修改全局模板。只有汇总分析形成明确建议并经确认后，才能把整改经验固化为硬规则。

整改记录表为 `pm_dictionary_rectifications`；模板改进建议和审批仍统一进入 `pm_dictionary_template_changes`，保证“问题 -> 修复 -> 分析 -> 模板变更 -> 新数据校验”的完整追溯链路。

### 6. 当前发布基线

当前基线为 `DDM-1.0.0`。它将本手册中的库元、表元、字段元、码值元、场景元、Mapping 规则元、涉及字段元和 Mapping 动作元作为受控元类型。

## 总目标

数据字典不是普通字段列表，而是银行监管报送项目里的 Mapping 工作台。它需要同时服务三类工作：

1. 业务访谈：清楚说明一个目标表、目标字段的业务口径和数据来源。
2. 开发实现：把字段 Mapping 逻辑结构化，后续可辅助生成 ETL / SQL / 脚本。
3. 排查检索：快速从字段、表、库、来源字段、码值、口径、场景定位到相关信息。

## 核心元模型

Mapping 中所有对象都应尽量按「元」来理解和存储：

| 元类型 | 含义 | 典型属性 |
| --- | --- | --- |
| 库元 | 一个数据源、数据集市、报送区或可信区库 | 库名、系统、环境、连接信息、说明 |
| 表元 | 一个数据源单元，可以是数据库表、文件、报表模型或报文结构 | 英文名、中文名、数据层级、载体类型、表口径、所属库 |
| 字段元 | 一个表字段 | 英文字段名、中文名、类型、长度、格式、字段说明、码值说明、备注 |
| 码值元 | 一组可复用的标准码值集合 | 码值集合名、值、说明、备注、排序 |
| 场景元 | 一组业务场景或取数分支 | 场景名称、业务口径、适用范围、优先级 |
| Mapping 规则元 | 某个场景下某个目标字段的加工规则 | 目标字段、动作类型、涉及字段、逻辑条件、转换状态、转换后 SQL、备注 |

元之间可以相互关联。字段引用必须优先使用结构化路径：`库.表.字段`。如果库或表暂时未知，也要保留可追溯的原始名称。

## Mapping 整体结构与填报模型

一个目标表的 Mapping 必须按「目标表 -> 场景口径 -> 字段 Mapping」三级结构维护，不能再把口径、字段逻辑、备注和涉及字段混在同一段自由文本里。

### 1. 主关系

| 层级 | 元类型 | 基数 | 职责 |
| --- | --- | --- |
| 目标表 | 表元 | 1 | 当前 Mapping 页正在生成的目标表、文件、报文或中间表 |
| 场景 | 场景元 | 1..N | 一个目标表可以有多个业务场景、取数分支或报送分支 |
| 口径 | 场景口径元 | 每个场景 1 套 | 描述该场景的 `FROM / JOIN / WHERE / GROUP BY / ORDER BY / LIMIT` 等记录级 SQL 规则 |
| 字段 Mapping | Mapping 规则元 | 每个场景下覆盖目标表字段 | 描述当前场景下每个目标字段的 `SELECT` 表达式生成规则 |
| 涉及字段 | 涉及字段元 | 0..N | 绑定口径或字段 Mapping 中用到的来源字段元 |
| 动作 | Mapping 动作元 | 0..N | 标准 JSON 动作，组成字段表达式或口径条件 |

严格边界：

1. 场景决定“一批记录怎么取”；字段 Mapping 决定“每个目标字段怎么生成”。
2. 口径只生成 `SELECT ...` 后面的取数范围；字段 Mapping 只生成 `SELECT` 中的字段表达式。
3. 字段 Mapping 使用到的来源表，必须出现在同场景口径的 `from` 或 `joins` 中。
4. 涉及字段必须优先绑定字段元；展示名称可以变，但绑定关系不能靠逻辑文本临时解析。
5. 备注只写解释、证据缺口、历史原因和人工确认点，不能替代口径或字段 Mapping 逻辑。

### 2. 场景口径标准属性

每个场景必须维护一套口径对象，推荐保存为独立元；兼容旧数据时可以临时从 Mapping 文本中解析，但新数据必须按结构化属性填写。

| 属性 | 是否必填 | 说明 |
| --- | --- | --- |
| 场景编码 | 是 | 同一目标表内唯一，例如 `scenario_1_domestic_loan_withdraw` |
| 场景名称 | 是 | UI title 展示，例如 `场景1 国内外汇贷款提款` |
| 适用说明 | 是 | 业务可读说明，说明这个场景何时适用 |
| 涉及表 | 是 | 来自 `from` 和 `joins` 的表元集合，优先绑定表元 |
| 涉及字段 | 条件必填 | `where`、`join.on`、`group_by`、`order_by` 中用到的字段元 |
| 口径逻辑 | 是 | 标准 JSON，表达取数范围和记录级条件 |
| SQL转换 | 系统生成 | 由口径逻辑实时转换，不作为人工主填字段 |
| 备注 | 否 | 证据、例外、暂存说明，不能写可转换逻辑 |
| 状态 | 是 | `draft`、`structured`、`complete`、`blocked`、`manual_only` |

口径 JSON 只允许表达记录级规则：

```json
{
  "op": "dataset",
  "from": {"table": "TransactionTab", "alias": "t"},
  "joins": [
    {
      "type": "left",
      "table": "Customer",
      "alias": "c",
      "on": {"source": "t.customer_code", "eq": {"source": "c.customerCode"}}
    }
  ],
  "where": {
    "and": [
      {"source": "t.status", "eq": "1"},
      {"source": "c.accountMainType.accountMainTypeCode", "in": ["12", "13"]}
    ]
  },
  "group_by": ["t.reference_number"],
  "order_by": [{"source": "t.created_at", "direction": "desc"}],
  "limit": 100,
  "remark": "仅取有效交易记录。"
}
```

### 3. 字段 Mapping 标准属性

每个场景下面，目标表的字段都应有一条字段 Mapping 记录；确实不生成的字段也要显式标为 `null`、`db_generated`、`manual_only` 或 `blocked`，不要缺行。

| 属性 | 是否必填 | 说明 |
| --- | --- | --- |
| 所属场景 | 是 | 绑定场景元 |
| 目标字段 | 是 | 绑定目标字段元 |
| 涉及字段 | 条件必填 | 字段表达式用到的来源字段元，优先结构化绑定 |
| 逻辑动作 | 是 | 标准 JSON 动作，表达字段级生成逻辑 |
| SQL转换 | 系统生成 | 由动作实时转换出的字段级 SQL 片段 |
| 状态 | 是 | `draft`、`structured`、`complete`、`blocked`、`manual_only` |
| 备注 | 否 | 只记录解释、证据缺口、人工确认点 |
| 排序 | 是 | 默认跟目标字段序一致 |

字段 Mapping JSON 只允许表达单个目标字段的生成规则：

```json
{"op":"direct","source":"TRN2.TXT.reference_number"}
{"op":"literal","value":"T"}
{"op":"code_mapping","source":"TransactionTab.paymentFlag","map":{"01":"C"},"else":"D"}
{"op":"case","when":[{"if":{"source":"Customer.accountMainType.accountMainTypeCode","in":["12","13"]},"then":{"source":"Customer.enCode"}}],"else":null}
```

### 4. 填报和展示约束

1. Mapping 页场景 tab 只切换场景；切换场景时口径和字段 Mapping 必须一起切换。
2. 口径展示区只展示「逻辑」和「SQL转换」摘要；涉及表、涉及字段、备注进入悬浮框模块化展示。
3. 字段 Mapping 表展示字段级逻辑和字段级 SQL；涉及字段列可以隐藏，但悬浮框必须完整展示涉及字段。
4. 字段 Mapping 悬浮框和口径悬浮框都按模块展示：涉及表/涉及字段、逻辑、SQL转换、备注。
5. SQL 转换统一由 JSON 动作引擎实时生成；数据库里的 `converted_sql` 只作为缓存或历史审计，不作为界面唯一来源。
6. JSON 不符合模板时，界面必须展示原文 JSON，并用红色标注 `规则不标准`；不得猜测转换。
7. 自然语言能结构化的必须改成标准动作；只有标准动作确实无法表达时，才允许 `sql` 或 `manual_logic`。

## 元属性规则

不同元有不同属性要求。不要把字段元的规则套到所有元上，也不要把展示规则误认为数据规则。

### 库元展示规则

库详情页需要有 title 栏，行为与表 title 一致：

1. 单击库 title，切换回该库详情页。
2. 双击库 title，固定或取消固定该库 title。
3. 库详情页中的「表清单摘要」必须展示该库下全部表清单。
4. 表清单摘要使用 table 方式展示，不用卡片堆叠。
5. 单击表行，右下角悬浮框展示该表详情。
6. 双击表行，打开该表，并把该表加入 title 栏。

### 字段元属性

字段元表示一个具体表字段。字段元必须优先维护这些核心属性：

| 属性 | 规则 |
| --- | --- |
| 英文字段名 | 使用数据库字段名，保持大小写和下划线等原始命名 |
| 中文字段名 | 使用经发文、文件规范、数据库注释或业务确认核验的业务中文名；不能用字段说明替代，也不能复制英文名充数。无可靠证据时保持为空 |
| 类型 | 使用数据库原生类型命名 |
| 长度 | 单独维护数据库长度或精度 |
| 格式 | 单独维护业务或监管格式要求，例如 `定长2位`、`最长60位`、`YYYY-MM-DD` |
| 字段说明 | 解释字段业务含义、填报要求、数据口径 |
| 码值说明 | 固定 key-value 规则，属于字段元属性，不属于普通备注 |
| 备注 | 补充说明、特殊约定、历史原因或临时注意事项；不要替代字段说明、码值说明或 Mapping 逻辑 |

字段类型必须统一，不要混用随意写法。优先使用目标数据库或来源数据库的原生类型，例如：

```text
varchar
char
text
number
decimal
int
bigint
date
datetime
timestamp
boolean
```

如果需要展示长度或精度，不要塞进类型属性，放到长度属性；如果是定长、最长位数、日期样式等具体格式要求，放到格式属性。例如：

| 类型 | 长度 | 格式 |
| --- | --- | --- |
| varchar | 64 | 最长64位 |
| char | 2 | 定长2位 |
| decimal | 20,2 | 数字，精度20,2 |
| date | - | YYYY-MM-DD |
| datetime | - | YYYY-MM-DD HH24:MI:SS |

不要把 `字符串`、`字符型`、`日期型`、`金额型` 这类中文描述放在类型属性；这些可以写在字段说明或备注中。
中文字段名为空代表“尚未核验”，不是缺省值允许随意补写。Agent 不得把英文名、字段代码或机器翻译直接写进中文字段名；需要补齐时必须先记录证据来源。
不要把 `定长2位`、`YYYY-MM-DD` 这类格式要求混入类型属性。格式属于字段元的独立属性，后续生成 Mapping 文档、测试数据和校验脚本时都应优先读取该属性。

码值说明不能长期作为字段里的散文本维护。标准模型中，码值应作为独立「码值元」存储，字段元通过绑定关系引用码值元。

码值元固定属性：

| 属性 | 规则 |
| --- | --- |
| 码值集合名 | 可读名称，例如 `是否标志码值`、`账户状态码值` |
| 值 | 真实入库或报送的码值，例如 `01`、`02`、`Y`、`N` |
| 说明 | 该码值的业务含义 |
| 备注 | 特殊约定、历史说明、适用条件；没有内容可以为空 |
| 排序 | 用于按业务顺序稳定展示 |

字段元只保存“绑定到哪个码值元”的关系，不应把大量码值写进备注或字段说明。展示字段详情时，码值说明必须按表格展示，固定列为：`值`、`说明`、`备注`。

为兼容历史 Mapping 导入数据，系统可以临时从字段的旧 `code_value` 文本中解析码值项，但 Agent 后续整理数据时，应逐步沉淀为独立码值元，再把字段元绑定到码值元。

旧文本导入时，推荐原始文本格式：

```text
01: 正常
02: 冻结
03: 注销
```

也可以使用 `=`，但同一个项目内必须保持一致：

```text
01=正常
02=冻结
03=注销
```

不推荐把码值写成一整句话，例如 `01表示正常，02表示冻结`。如果从原始 Mapping 文档导入时遇到这种写法，Agent 应保留原意并整理成码值元：一行一个值，分别维护说明和备注。

### 表元属性

表元不是狭义的数据库表，而是 Mapping 中的数据源统称。它可以代表数据库表，也可以代表文件、报文、接口返回结构或报表模型，但必须通过属性区分清楚。

表元必须优先维护这些核心属性：

| 属性 | 规则 |
| --- | --- |
| 英文名 | 数据库表名、文件名、报文节点名或模型英文名 |
| 中文名 | 业务可读名称，不能用表口径代替 |
| 分组 | 用于对表元进行业务或技术分组，例如客户、账户、交易、报文、公共代码等 |
| 数据层级 | 固定码值：`源表层`、`中间层`、`报表层`、`报文层` |
| 载体类型 | 固定码值：`数据库`、`文件`、`XML报文` |
| 所属库 | 如果载体是数据库，记录库元；如果是文件，记录文件来源或目录归属 |
| 表口径 | 说明这张表/文件/报文结构承载什么业务数据 |
| 说明 | 补充用途、来源限制、生成方式、上下游关系 |

数据层级用于回答“它处在加工链路的哪一层”：

```text
源表层：直接来自上游系统或原始落地数据。
中间层：加工过程中的临时表、宽表、主题层或汇总过程表。
报表层：面向监管报表、业务报表或查询展示的结果模型。
报文层：面向监管接口、文件报送、可信区交互的报文或文件结构。
```

载体类型用于回答“它以什么形式存在”：

```text
数据库：真实数据库表、视图、物化视图或结构化库表模型。
文件：Excel、CSV、TXT、JSON、定长文件等。
XML报文：监管 XML 报文、接口 XML 报文等有明确节点结构的报文文件。
```

不要把数据层级和载体类型混在一个字段里。比如一张监管 XML 报文应写成：数据层级=`报文层`，载体类型=`XML报文`；一张上游 CRM 客户表应写成：数据层级=`源表层`，载体类型=`数据库`。

### 表元属性补充：监管 XML 报文

监管 XML 报文按正式发文、接口规范或可核验 XSD/XML 示例建模。一个监管报文、一个业务接口或一个可独立报送的 XML 结构应建成一个表元；表元数据层级写 `报文层`，载体类型写 `XML报文`，中文名推荐使用 `[报文]业务对象`，不得把内部物理表名或项目代际写入通用中文名。

监管报文表英文名必须优先使用发文中“金融机构信息系统生成的接口文件的命名规则”定义的数据类型/接口文件类型名，即应用类型代码加接口文件类型代码，例如 `FALEJ` 表示 `FAL + EJ`，对应 `E03-3表：外资承运人国际运输服务统计表（仅国际运输调查主体填写）`。不得用表号 `E03_3`、临时内部名 `SAFE_MSG_E03_3` 或物理落地表名替代正式接口文件类型名；只有发文未给出接口文件类型代码时，才允许使用稳定内部名，并必须在 `extra` 中标明命名证据缺口。

XML 报文字段元必须遵循以下规则：

| 属性 | 规则 |
| --- | --- |
| 英文字段名 | 使用 XML 路径，保留节点层级，例如 `REC.ACTIONTYPE`、`REC.CUSTOMS.CUSTOM.CUSTOMN` |
| 中文字段名 | 只使用发文数据字典、节点说明或业务确认中的中文内容；容器节点没有业务中文名时可写 `XML容器节点` |
| 类型 | 使用模板标准类型；监管原始类型如 `字符型，18`、`数值型，22.2` 写入格式或 `extra.rawType` |
| 长度 | 单独维护监管长度或精度；不能把长度混入类型 |
| 格式 | 维护监管原始类型、日期格式、金额精度、定长/最长位数等 |
| 字段说明 | 维护发文校验、填报口径或节点说明 |
| 字段顺序 | 按 XML 示例或发文数据字典顺序维护 `field_order` |
| 载体类型 | 字段元 `carrier_kind` 写 `xml` |

XML 容器节点和叶子节点都可以作为字段元；容器节点类型写 `xml_node`，说明为 `XML 容器节点`，不写 Mapping 来源逻辑。监管报文本身的 Mapping 逻辑表示“报文节点数据怎么生成”，不是 XML 节点结构说明；只有拿到存储过程、SQL、接口组装代码或业务 Mapping 文档证据时，才能填写 Mapping 元和涉及字段元。

发文中只有业务描述、截图、外部系统引用或“见某系统”说明，但没有 XML 节点名、字段名或可核验结构时，不得生成正式字段元；可以在整理文档中记录为“结构待确认”。不得用中文内容、序号或字段说明反推 XML 节点名。

### 库元属性

| 属性 | 是否必填 | 规则 |
| --- | --- | --- |
| 库编码 | 是 | 项目内唯一；使用稳定技术编码，不随展示名称随意变化 |
| 库名称 | 是 | 使用业务或技术可读名称 |
| 系统类型 | 是 | 固定码值：`source_system`、`ods`、`data_mart`、`reporting`、`message`、`integration`、`other` |
| 资产层级 | 是 | 固定码值：`源数据层`、`贴源层`、`中间层`、`报表层`、`报文层`、`公共层` |
| 数据库类型 | 条件必填 | 当库元承载数据库、贴源库、中间库、报表库或测试实体库时必填；首轮固定码值：`postgresql`、`sqlserver`、`unknown` |
| SQL 方言 | 条件必填 | SQL 组装使用的语法方言，默认跟数据库类型一致；首轮固定码值：`postgresql`、`sqlserver` |
| 环境 | 是 | 固定码值：`DEV`、`SIT`、`UAT`、`PROD`、`LOCAL`、`UNKNOWN` |
| 用途说明 | 是 | 说明该库在加工链路中的职责，不能只写“数据库” |
| 连接信息 | 条件必填 | 有权限且确有连接时维护；无权限时写明“未配置/待确认”，不得编造凭证；密码、token、证书不得明文入库 |
| 实体同步策略 | 否 | 固定码值：`metadata_only`、`create_schema_allowed`、`create_table_allowed`、`insert_test_data_allowed`、`readonly` |
| 备注 | 否 | 仅记录边界、历史或临时说明 |

库元的数据库类型决定 SQL 生成器的默认行为。字段 Mapping 和场景口径只保存标准 JSON 动作，不保存厂商语法分支；界面展示 SQL 时根据当前目标库元的 `SQL 方言` 生成对应语法。例如：

| 标准动作 | PostgreSQL | SQL Server |
| --- | --- | --- | --- |
| 随机数 | `RANDOM()` | `RAND(CHECKSUM(NEWID()))` |
| 日期解析 | `TO_DATE(value, 'YYYYMMDD')` | `CONVERT(date, value, 112)` |
| 字符串截取 | `SUBSTRING(value FROM start FOR length)` | `SUBSTRING(value, start, length)` |
| 分隔取段 | `SPLIT_PART(value, delimiter, index)` | `JSON_VALUE(CONCAT(...), '$[index]')`，复杂转义场景必须改为受控 SQL |
| 空值保护 | `NULLIF(value, compare)` | `NULLIF(value, compare)` |

连接信息必须按结构化 JSON 保存到库元 `extra.connection`，推荐结构：

```json
{
  "dbType": "postgresql",
  "sqlDialect": "postgresql",
  "connection": {
    "host": "127.0.0.1",
    "port": 5432,
    "database": "rich_test",
    "schema": "public",
    "username": "rich",
    "secretRef": "keychain://rich/vtb-safe/postgres",
    "ssl": false
  },
  "entitySyncPolicy": "metadata_only",
  "role": "test_entity_store"
}
```

安全规则：

1. `password`、`accessToken`、私钥、证书内容不得写入数据字典数据库。
2. 本机开发可使用系统 Keychain、`.env` 或用户确认的 secretRef；界面只展示是否已配置，不展示明文。
3. 测试连接、建表、写入测试数据都必须记录操作结果和时间；失败时展示错误原因，不静默吞掉。
4. 默认策略是 `metadata_only`，只有用户明确开启实体同步策略后，才允许创建实体库表或写入测试数据。

### 实体库与测试数据落库规则

数据字典里的库元、表元、字段元是元数据；实体库是由元数据生成出来的真实数据库对象。二者必须可追溯绑定，但不能混为同一个东西。

表元可以维护实体同步属性：

| 属性 | 是否必填 | 说明 |
| --- | --- | --- |
| 实体库元 | 条件必填 | 该表要同步到哪个可连接库元 |
| 实体 schema | 否 | 未填写时使用库元连接默认 schema |
| 实体表名 | 是 | 默认使用表元英文名，可按目标数据库命名规则转换 |
| 实体同步状态 | 是 | `not_created`、`created`、`drifted`、`failed`、`unknown` |
| 最近建表时间 | 否 | 最近一次创建或校验实体表的时间 |
| 最近写入测试数据时间 | 否 | 最近一次测试数据落库时间 |
| 实体同步备注 | 否 | 字段类型无法映射、权限不足、结构差异等说明 |

测试数据页可以提供两个执行按钮：

1. `创建实体库`：根据当前表元和字段元生成目标数据库 DDL，创建或校验实体表。
2. `写入测试数据`：将当前测试数据表格中的行按字段映射写入实体表。

执行规则：

1. `创建实体库` 按库元 SQL 方言生成 DDL；字段类型使用字段元的 `类型 / 长度 / 格式` 进行方言映射。
2. 默认不覆盖已有实体表。若实体表已存在，先做结构校验；字段缺失、类型不一致、长度不一致时标记 `drifted`，需要用户确认后才允许变更。
3. 测试数据落库前必须确保实体表已创建且结构一致；否则按钮显示不可执行或进入错误状态。
4. 测试数据写入应支持 `append`、`truncate_insert` 两种模式；默认 `append`，`truncate_insert` 需二次确认。
5. 写入后返回写入行数、失败行数、失败原因；界面同步展示结果。
6. 文件上传解析出来的测试数据和手工测试数据使用同一套落库流程。
7. 所有执行行为只针对用户配置的测试/开发实体库，不得默认连接生产库；当环境为 `PROD` 时，创建和写入按钮默认禁用。
8. 首轮页面触发的测试数据写入单次最多 1000 行，避免大文件一次性把前后端请求体撑爆；超过 1000 行的数据应改为服务端读取上传文件并分批落库。

### 表元属性补充：文件与贴源关系

当表元载体类型为 `文件` 时，必须维护：文件名规则、文件路径、编码、记录格式、分隔符或定长规则、表头规则、导入规则。尚未获得证据时可填 `待确认`，但不可留空或猜测。

文件表的中文名不是必填猜测项：只有在发文、文件规范、ETL 配置、业务确认或一对一贴源入库关系中能找到明确业务对象时才填写；没有可靠证据时保持为空，界面以文件名作为主显示。文件入库到唯一贴源表且贴源表中文名已确认时，源文件中文名可以参考贴源表中文名派生，但必须保留文件载体语义。推荐格式为 `[层级]业务对象`，例如源文件写 `[源文件]账户信息`，对应贴源表写 `[贴源]账户信息`；不得直接复制英文文件名充当中文名，也不得把项目代际、产品名或实现来源（如 OneGen）混入通用中文表名，除非业务对象名称本身包含这些词。

仅参与文件名匹配、数量校验、到达性校验或批次完整性校验，且没有独立字段结构、业务口径或入库承接字段的文件，不应建成正式表元。此类文件可作为表说明、批次规则或证据备注记录；如果已误建表元，删除时必须同时清理字段、搜索索引、字段关联、整改记录和其他下级数据。

文件字段必须额外维护以下结构化属性：`解析方式`（分隔符/定长/其他）、`分隔符或定长规则`、`字段序号`、`源文件名`、`对应贴源字段`。字段说明是这些属性的组合展示，例如：`源文件：AIF2.TXT；解析方式：分隔符；分隔/定长规则：|；字段序号：第 3 字段；对应贴源字段：customer_id`。

文件字段的 `source_field_order` 是用于展示与导入的正式序号。`SAFE_SOURCE` 字段清单必须按它升序展示，绝不能按字段英文名推断文件顺序。未从文件样本或 ETL 配置确认的位置保持为空/待确认，不得自动补号。

文件字段与数据库字段是两个可追溯的字段元，不得把文件字段降级为匿名文本列。字段元必须维护 `carrier_kind`：`file` 代表文件原始字段，`database` 代表数据库物理字段；后续新增载体必须先扩展模板枚举。已确认的文件字段必须具备英文名、中文名、源文件名、解析方式、分隔符/定长规则和字段序号，并通过字段关联绑定对应的数据库字段元。关联记录至少保存目标库、目标表、目标字段和目标中文名；文件入库与数据库出文件都复用这一关联。文件字段可保留原始文本类型，数据库字段仍以物理数据库类型、长度和格式为准；两端之间的转换只记录在 Mapping 元中，不能以猜测补齐。

源文件字段到贴源字段的对应关系只表示“文件入库承接关系”，不是源文件自身的 Mapping 来源逻辑。除非有调度、接口、上游系统或生成脚本证据能说明该文件如何生成，否则源文件表和源文件字段的 Mapping 逻辑必须保持为空/待确认；不得把 `源文件 -> 贴源表` 写成源文件层 Mapping，也不得在源文件 Mapping 页展示贴源字段作为“涉及字段”。这类关系应通过字段关联、关联关系页、字段说明或表说明表达。

贴源字段的 Mapping 涉及字段必须引用源字段元的真实英文名和表元英文名，例如源字段元为 `CIF2.TXT.customer_id` 时，涉及字段必须写 `CIF2.TXT.customer_id`。不得把目标贴源字段名 `customerId`、自动驼峰/下划线转换结果或展示别名写进涉及字段，否则前端无法绑定到源字段元。

所有字段元另有通用 `field_order` 属性，字段清单必须优先按该属性升序展示，不得默认按英文名排序：数据库/贴源/中间表按数据库物理列序；监管报表、报文和 XML 结构按发文或报文标签顺序；源文件仍以 `source_field_order` 为准。没有可靠来源时保留待确认，并在已确认字段之后按导入记录稳定展示，不能回退成英文名排序。

字段元输入不得把多个字段名合并写成一个字段元，例如 `ActionType/ActionDesc/Remark` 不能作为一个英文字段名入库。整理稿中如果为了节省篇幅出现合并行，导入程序必须拆成多个独立字段元，并在 `extra.expandedFrom` 保留原合并文本；如果无法拆分出明确字段名，则只记录为待确认项，不写入字段元。

尚未取得文件样本或 ETL 配置时，解析方式、分隔/定长规则与字段序号统一写为 `待确认`；不得根据贴源表字段名、历史项目经验或英文字段名猜测顺序、分隔符、长度和业务中文名。

当表元数据层级为 `贴源层` 时，必须维护：关联源文件/源表、承接方式、关联状态。贴源字段必须关联对应源字段元；如果原始字段列号、分隔规则尚未核验，关联状态必须为 `待文件/ETL核验`。

### 场景元属性

| 属性 | 是否必填 | 规则 |
| --- | --- | --- |
| 场景名称 | 是 | 同一目标表内唯一、业务可读 |
| 场景编码 | 是 | 同一目标表内唯一、稳定标识 |
| 业务口径 | 是 | 说明适用范围、取数边界、来源和与其他场景的差异 |
| 优先级 | 是 | 正整数；存在多场景命中时用于确定处理顺序 |
| 启用状态 | 是 | 固定码值：`active`、`inactive`、`draft` |
| 备注 | 否 | 只写补充信息，不替代业务口径 |

### Mapping 规则元属性

Mapping 规则元是从业务 Mapping 文档走向可生成 SQL 的核心。它不是一段孤立文本，而是由「目标字段元 + 场景 + 涉及字段元 + 动作链 + 转换结果」共同组成的结构化元。

Mapping 规则元只表示“某个业务场景下，某个目标字段如何生成”。涉及字段必须拆成独立的涉及字段元，动作必须拆成可排序的动作元。逻辑展示时引用涉及字段元，不直接硬写字段文本；这样字段元、表元、库元变更后，展示和 SQL 生成可以沿关系自动更新。

Mapping 规则元必须优先维护这些核心属性：

| 属性 | 规则 |
| --- | --- |
| 目标字段 | 当前规则最终写入的字段元 |
| 所属场景 | 当前规则属于哪个业务场景或取数分支 |
| 涉及字段元 | 当前 Mapping 用到的字段引用集合，每条引用可绑定一个字段元 |
| 动作链 | 多个可排序动作元的组合，例如先关联、再条件判断、再格式处理 |
| 逻辑说明 | 当动作链不足以表达时，保留人工可读的补充说明 |
| 转换状态 | 说明当前 Mapping 是否可稳定转换为 SQL |
| 转换后 SQL | 当状态为完成时，存放可复核、可生成 ETL 的 SQL 片段 |
| 备注 | 无法结构化、历史原因、人工确认点或特殊边界 |

### 涉及字段元属性

涉及字段元是 Mapping 元和字段元之间的中间元，不能只做成 Mapping 里的文本数组。

| 属性 | 规则 |
| --- | --- |
| 所属 Mapping | 绑定到某条 Mapping 规则元 |
| 绑定字段元 | 能定位到系统字段时，必须关联字段元 |
| 字段引用路径 | 展示用路径，格式优先为 `库.表.字段`；未绑定时也要保留文本路径 |
| 别名 | SQL 或口径中的字段别名，例如 `T1`、`src_customer_id` |
| 作用 | 可选，说明该字段在逻辑中的作用，如主取值字段、关联键、过滤条件、分组字段 |
| 备注 | 字段引用不确定、来自文件、历史口径等补充说明 |

涉及字段元展示规则：

1. 已绑定字段元的标签用绿色。
2. 未绑定字段元、只有文本路径的标签用蓝色。
3. 动作元引用涉及字段元，不直接复制字段名文本。
4. 如果字段元名称、表名、库名发生变化，涉及字段元展示应根据绑定关系自动刷新。

### Mapping 动作元属性

一个 Mapping 规则可以有多个动作元。动作元按 `sort_order` 组成动作链，用来准确表达 SQL 生成过程。

| 属性 | 规则 |
| --- | --- |
| 所属 Mapping | 绑定到某条 Mapping 规则元 |
| 动作类型 | 固定动作码值，说明本动作采用哪类加工动作 |
| 使用字段 | 关联到本 Mapping 下的涉及字段元 |
| 条件 | WHERE、CASE WHEN、JOIN ON、过滤条件、优先级条件等 |
| 表达式 | 当前动作生成的表达式或中间结果 |
| 结果 | 当前动作产出的结果说明，可用于拼接最终 SQL |
| 备注 | 当前动作的特殊边界或人工确认点 |

动作类型必须使用固定码值，避免每个 Agent 自己造词：

| 动作类型 | 含义 | SQL 生成方向 |
| --- | --- | --- |
| `direct` | 直取字段，不做加工 | `source_col AS target_col` |
| `random` | 随机生成数字 ID、UUID 等系统值 | `CAST(FLOOR(RANDOM()...) AS BIGINT)`、`UUID()` |
| `null` | 置空、不赋值 | `NULL AS target_col` |
| `literal` | 默认值、固定值、常量 | `'固定值' AS target_col` |
| `param` | 运行参数，抽取或验证时由页面输入 | `:paramName AS target_col` |
| `case` | 条件判断，可嵌套其他动作作为结果 | `CASE WHEN ... THEN ... ELSE ... END AS target_col` |
| `join` | 关联取值 | 需要维护 JOIN 表、JOIN 条件和取值字段 |
| `cast` | 类型转换 | `CAST(source_col AS type)` |
| `split_part` | 按分隔符取第 N 段 | `SPLIT_PART(source_col, delimiter, index)` |
| `concat` | 字段或常量拼接 | `CONCAT(...)` |
| `round` | 数值四舍五入 | `ROUND(expr, scale)` |
| `divide` / `multiply` / `add` / `subtract` | 四则运算，可嵌套字段、常量和其他动作 | `(left / right)` 等 |
| `nullif` | 空值或零值保护，常用于除法分母 | `NULLIF(expr, compare)` |
| `aggregate` | 汇总计算 | `SUM`、`COUNT`、`MAX`、`MIN`、`GROUP BY` |
| `code_mapping` | 码值转换 | 通过 CASE WHEN 或码值元映射转换 |
| `deduplicate` | 去重、取最新、取唯一 | `ROW_NUMBER`、`DISTINCT`、排序优先级 |
| `filter` | 过滤条件 | WHERE 条件，不单独产出字段但影响规则 |
| `sql` | 已确认无法用标准动作稳定表达的 SQL 表达式 | 直接使用受控 SQL 表达式 |
| `manual_logic` | 复杂自然语言说明，暂不能结构化 | 不自动生成 SQL |

填写逻辑时必须优先使用中文动作对应的 JSON 标准结构。界面展示中文动作，底层保存 `op` 固定码值；后续 SQL 由动作链实时推导。常用写法如下：

```json
{"op":"direct","source":"TRN2.TXT.reference_number"}
{"op":"random","type":"number","length":18}
{"op":"null"}
{"op":"literal","value":"T"}
{"op":"param","name":"importDate"}
{"op":"cast","source":"BLN2.TXT.ldbl","to":"DECIMAL(18,2)"}
{"op":"split_part","source":"BLN2.TXT.bus_date","delimiter":"-","index":1}
{"op":"case","when":[{"if":{"source":"BLN2.TXT.currency","eq":"RUR"},"then":"RUB"}],"else":{"source":"BLN2.TXT.currency"}}
{"op":"case","when":[{"if":{"source":"Customer.accountMainType.accountMainTypeCode","in":["12","13"]},"then":{"source":"Customer.enCode"}}],"else":null}
{"op":"code_mapping","source":"TransactionTab.paymentFlag","map":{"01":"C"},"else":"D"}
```

更复杂的计算也应先尝试通过标准动作组合表达。例如“先按 `@` 取第 2 段，再转数值，再做倒数并保留 8 位”：

```json
{
  "op": "round",
  "value": {
    "op": "divide",
    "left": 1,
    "right": {
      "op": "nullif",
      "value": {
        "op": "cast",
        "value": {"op": "split_part", "source": "TRN2.TXT.payment_direction", "delimiter": "@", "index": 2},
        "to": "DECIMAL(18,8)"
      },
      "compare": 0
    }
  },
  "scale": 8
}
```

只有满足以下任一条件，才允许使用 `sql` 动作：

1. 需要窗口函数、复杂 JOIN、递归、厂商特有函数，当前动作码值无法表达。
2. 涉及业务算法尚未拆清，已由人工确认暂时保留 SQL。
3. 新动作类型尚未进入模板版本，先用 `sql` 暂存，并同步创建模板变更建议。

不能把“当文件字段数大于 41 时直取”“同上场景”“参考 Java 逻辑”等备注性文字写进逻辑动作；这些内容应写入备注或场景口径。

### Mapping 场景口径规则

字段 Mapping 规则只负责生成 `SELECT` 中的单个字段表达式；场景口径规则负责生成字段表达式后面的取数范围 SQL，包括 `FROM`、`JOIN`、`WHERE`、`GROUP BY`、`ORDER BY`、`LIMIT`。字段逻辑中用到的来源表，必须能在当前场景口径的 `from` 或 `joins` 中找到；否则该场景不能视为可完整生成 SQL。

场景口径同样必须使用标准 JSON。界面展示时分成「涉及表」「涉及字段」「逻辑」「SQL转换」；不能解析的原文 JSON 或自然语言必须红色标注，不自动转换。

口径标准写法：

```json
{
  "op": "dataset",
  "from": {"table": "Customer", "alias": "c"},
  "joins": [
    {
      "type": "left",
      "table": "Account",
      "alias": "a",
      "on": {"source": "c.customerId", "eq": {"source": "a.customerId"}}
    }
  ],
  "where": {
    "and": [
      {"source": "c.status", "eq": "1"},
      {"source": "c.accountMainType.accountMainTypeCode", "in": ["12", "13"]}
    ]
  },
  "group_by": ["c.customerId"],
  "order_by": [{"source": "c.createdAt", "direction": "desc"}],
  "limit": 100,
  "remark": "仅取有效客户账户。"
}
```

口径条件与字段 Mapping 的 `case.if` 共用条件表达式：支持 `eq`、`ne`、`gt`、`gte`、`lt`、`lte`、`like`、`in`、`not_in`、`and`、`or`、`not`。

动作组合示例：

| 顺序 | 动作 | 使用字段元 | 表达 |
| --- | --- | --- | --- |
| 1 | `join` | 客户表.客户号、账户表.客户号 | 通过客户号关联客户和账户 |
| 2 | `condition` | 账户表.账户状态 | 只取正常账户 |
| 3 | `format` | 账户表.开户日期 | 将 `YYYYMMDD` 转成 `YYYY-MM-DD` |
| 4 | `direct` | 账户表.账户号 | 生成目标字段账户号 |

转换状态固定码值：

| 状态 | 含义 |
| --- | --- |
| `draft` | 已录入，但尚未分析是否可转换 |
| `structured` | 已拆成动作、涉及字段、条件、结果，但还没有生成 SQL |
| `complete` | 可完全通过动作描述生成 SQL，且 `转换后 SQL` 已维护 |
| `blocked` | 缺少字段、表、码值、关联条件等关键信息，暂不能生成 SQL |
| `manual_only` | 逻辑过于复杂或依赖人工判断，无法通过动作模板稳定转换 |

只有满足以下条件，状态才可以置为 `complete`：

1. 目标字段明确。
2. 涉及字段都已列出，能绑定字段元的必须完成绑定。
3. 动作链完整，动作类型使用固定码值，不使用含糊描述。
4. 每个动作使用的字段都引用涉及字段元。
5. 条件、表达式和结果足够生成 SQL。
6. `转换后 SQL` 已写出，且能被人工复核。

如果逻辑很复杂，无法用固定动作链描述，不要强行拆解。此时状态设为 `manual_only`，动作链中至少保留一条 `manual_logic` 动作，逻辑说明字段保留完整说明，`转换后 SQL` 留空。

`转换后 SQL` 推荐只保存字段级 SQL 片段，而不是整段完整作业 SQL。例如：

```sql
CASE
  WHEN T1.STATUS = '1' THEN '01'
  WHEN T1.STATUS = '2' THEN '02'
  ELSE '99'
END AS TARGET_STATUS
```

如果当前规则需要 JOIN 或汇总，可以在规则中记录依赖，再由上层作业组装完整 SQL。

## 固定展示模版

### 1. 字段设计

字段设计用于展示目标表的字段清单。它应保持类 Navicat 的表格体验：

字段设计表默认必须按顺序属性展示：源文件字段按 `source_field_order` 升序；数据库、贴源、中间、报表和报文字段按 `field_order` 升序；没有顺序属性的字段只能排在已确认顺序字段之后并保持导入顺序，不得按英文字段名排序。

右侧字段区顶部应有当前表 title 栏，用来展示当前选中的表。title 交互规则：

1. 单击 title：切换回该表。
2. 双击 title：钉住该表；再次双击取消钉住。
3. 已钉住 title 需要用不同颜色标识。
4. 已钉住 title 常驻在 title 栏，后续打开的新表 title 跟在后面。
5. 左侧表清单不展示多余的「连接」标题小行，减少视觉噪音。

| 列 | 规则 |
| --- | --- |
| 序号 | 只用于阅读定位，不作为业务字段 |
| 英文名 | 固定列，左右滚动时不能消失 |
| 中文名 | 固定列，左右滚动时不能消失 |
| 类型 | 使用数据库原生类型命名，高亮、清楚展示 |
| 长度 | 高亮、清楚展示 |
| 格式 | 展示字段格式要求，例如定长、最长、日期格式；点击可在右下角悬浮框查看完整内容 |
| 字段说明 | 一行放不下时只做简略展示，点击右下角悬浮框查看完整内容 |
| 码值说明 | 字段绑定码值元时展示码值项数量；点击右下角悬浮框查看完整表格；兼容旧文本时也要尽量解析成表格 |
| 备注 | 一行放不下时只做简略展示；有内容时在悬浮框中作为独立区块展示 |

字段属性表头和数据列必须对齐。带序号的表格，表头和行数据必须使用同一套列宽配置。

字段设计表按整行查看字段元详情。点击字段行任意位置，都应打开同一个悬浮框，展示该字段的完整核心信息：

1. 悬浮框抬头第一行高亮字段英文名和中文名。
2. 悬浮框抬头下方用不同颜色标签展示类型、长度、格式。
3. 正文区分层展示字段说明、码值说明和备注。
4. 码值说明必须优先使用码值元表格展示，固定列为 `值`、`说明`、`备注`；历史文本能解析时也要转成同样表格。
5. 备注只有有内容时才展示，不要占用空白视觉区域。
6. 不要用单元格点击切换不同悬浮框内容，避免同一个字段的信息被拆散。

### 2. Mapping

Mapping 页不是简单把文本堆出来，必须按业务场景分组：

1. 第一层是场景 title，例如 `场景1`、`场景2`、`场景3`。
2. 场景之间使用 title/tab 切换，一次只展示当前场景。
3. 每个场景下面先展示「口径」。
4. 口径下面展示字段 Mapping 表。
5. `测试数据` 后面必须有 `表说明` title，用来展示当前表元属性。

表说明页固定展示：

| 区块 | 内容 |
| --- | --- |
| 表元头部 | 中文名、英文名 |
| 属性摘要 | 分组、数据层级、载体类型、字段数量 |
| 表说明 | 表元的用途、来源限制、生成方式、上下游关系 |
| 表口径 | 这张表/文件/报文结构承载的业务数据口径 |
| 字段类型摘要 | 当前表字段类型数量分布 |

字段 Mapping 表固定列：

| 列 | 规则 |
| --- | --- |
| 序号 | 只用于当前场景内定位 |
| 字段名 | 目标字段英文名，固定列 |
| 中文名 | 目标字段中文名，固定列 |
| 逻辑 | 根据动作链组合展示条件、加工规则、取值方式、得出结果 |
| SQL转换 | 根据动作链和逻辑实时推导字段级 SQL；能稳定转换则展示 SQL，不能转换则显示 `无法转换` |
| 备注 | 写当前 Mapping 规则的补充说明；不能替代逻辑，也不要塞入涉及字段 |

字段 Mapping 表可选列：

| 列 | 规则 |
| --- | --- |
| 动作 | 展示动作链摘要，例如 `join -> condition -> format -> direct` |
| 状态 | 使用固定转换状态，例如 `draft`、`structured`、`complete`、`blocked`、`manual_only` |
| 涉及字段 | 默认可隐藏；需要展示时只展示涉及字段元标签，不写加工逻辑 |

Mapping 表按字段行查看详情。点击字段行任意位置，都应打开同一个悬浮框，组合展示「动作链 + 转换状态 + 涉及字段元 + 逻辑说明 + SQL转换结果」，有备注时追加独立备注区块，不要把涉及字段、逻辑和备注拆成多个不同弹框。

SQL 转换列是 Mapping 逻辑的实时校验器：

1. 如果逻辑已经标准化为固定动作链，且涉及字段元、条件、表达式都明确，则生成字段级 SQL 片段。
2. 如果逻辑仍是自然语言、缺少字段绑定、缺少条件或表达式不明确，则显示 `无法转换`。
3. `SQL转换` 列展示摘要，完整 SQL 进入悬浮框查看。
4. 这列不能人工随意填写，它应由 Mapping 元的动作链和涉及字段元实时推导；后端落库字段为 `转换后 SQL`。

涉及字段标签需要区分绑定状态：

1. 如果涉及字段能绑定到系统中的字段元，标签用绿色。
2. 如果只是未绑定的文本引用，标签保持蓝色。
3. Mapping 逻辑正文里凡是出现涉及字段元引用，都必须用字段标签包裹展示，不能混成普通文本。
4. 逻辑正文里的字段标签点击后，应打开该字段元所在表的详情 title，并定位到该字段。
5. 悬浮框展示涉及字段时使用两列表格：左列是英文 `库.表.字段`，右列是中文库/表/字段说明。不要在悬浮框里只堆标签。

### 3. 口径

口径是场景级说明，不是字段级说明。它回答：

- 当前场景适用于什么业务情况。
- 当前场景从哪些源表或源模型取数。
- 当前场景生成目标表记录的边界条件。
- 和其他场景的区别是什么。

口径可以折叠展开，默认展示应简洁，避免挤占字段 Mapping 表空间。

### 4. 涉及字段

涉及字段只做字段引用清单，不混写逻辑。推荐格式：

```text
库.表.字段
库.表.字段
库.表.字段
```

如果存在别名或临时表，可以补充为：

```text
库.表.字段 as 别名
临时表.字段
```

涉及字段应尽量结构化，后续用于：

- 字段血缘展示。
- 全局搜索。
- 影响分析。
- SQL / ETL 生成前的依赖确认。

### 5. 逻辑

逻辑列负责说明如何使用「涉及字段」得到目标字段结果。它可以包含：

- 直接映射。
- 条件判断。
- 码值转换。
- 拼接、截取、格式化。
- 默认值、空值处理。
- 多来源优先级。

逻辑中出现字段时，应尽量引用「涉及字段」里已经列出的字段。不要把大量字段引用只藏在逻辑正文里。

### 6. 码值说明

码值说明优先按 key-value 展示：

| Key | 说明 |
| --- | --- |
| 01 | 示例说明 |
| 02 | 示例说明 |

如果原始数据暂时无法拆分，先保留原文，但后续应逐步整理成 key-value。

### 7. 长文本展示

字段说明、码值说明、备注、涉及字段、逻辑等一行展示不全的属性，不应撑爆表格。规则：

1. 表格中只展示简略内容。
2. 点击字段行或 Mapping 行后，用右下角悬浮框展示完整内容。
3. 不同属性使用不同展示方式：
   - 字段说明：段落文本。
   - 码值说明：优先 key-value 表。
   - Mapping 行：组合展示涉及字段标签列表 + 保留换行的逻辑块；有备注时展示独立备注区块。
4. 悬浮框抬头统一为两行：第一行高亮显示当前字段/元名称，第二行显示当前属性名称。
5. 悬浮框支持收起、展开、调整大小，并记住大小。

## 数据录入规则

新增或更新 Mapping 数据时，Agent 必须遵守：

1. 不要把一个表的所有 Mapping 逻辑混成一段大文本。
2. 不要把场景、口径、字段逻辑、涉及字段混在同一个字段里。
3. 不要自动脑补业务口径；来源不清楚时标注「待确认」。
4. 不要为了展示好看修改用户原始业务含义。
5. 用户给出的 Excel、截图、访谈记录，应先解析成结构化草稿，再写入数据层。
6. 写入后要能通过全局搜索查到字段、表、码值、场景、涉及字段和逻辑关键词。

### 项目分析准入规则

实际项目代码、数据库、脚本、Excel、发文、截图或访谈记录进入 Rich 前，必须先被当作“证据”处理，不能直接当作“已确认元属性”写入。

Agent 分析项目时必须先产出结构化草稿，草稿至少包含：

| 属性 | 规则 |
| --- | --- |
| 证据来源 | 文件路径、数据库对象、SQL/存储过程、发文名称、截图名称或访谈记录来源 |
| 证据类型 | 固定码值：`physical_schema`、`etl_sql`、`source_file_sample`、`regulatory_doc`、`code_logic`、`interview`、`screenshot`、`unknown` |
| 可确认元类型 | 本证据能支持的元类型，例如库元、表元、字段元、码值元、场景元、Mapping 规则元 |
| 可确认属性 | 本证据能直接证明的属性清单 |
| 不能确认属性 | 容易被误填、但本证据不能证明的属性清单 |
| 冲突说明 | 和现有字典、其他证据或模板规则冲突时必须写明 |
| 建议动作 | 固定码值：`write_metadata`、`create_rectification`、`needs_user_confirmation`、`ignore` |

只有当证据能直接支持某个元属性时，才允许写入该元属性。证据只能间接暗示、依赖业务判断或存在冲突时，不得写入正式元属性，应创建整改或待确认项。

### 证据到元属性的边界

| 证据 | 可以确认 | 不得据此确认 |
| --- | --- | --- |
| 数据库物理表结构 | 表英文名、字段英文名、物理类型、长度、主键/可空、物理列序 | 中文名、业务口径、码值含义、完整 Mapping 逻辑 |
| SQL / 存储过程 | 明确的来源表字段、过滤条件、JOIN 条件、默认值、CASE 条件、字段级 SQL 片段 | 未出现在 SQL 中的场景口径、码值全集、业务中文名 |
| 源文件样本 | 文件名、分隔符/定长形态、样本列序、样本值形态 | 全量字段含义、长期格式规则、未出现码值的含义 |
| 发文/接口规范 | 报送字段中文名、格式、校验、监管码值、业务说明 | 本项目实际落地库表名、实际 ETL 来源、未写明的内部中间表逻辑 |
| 业务代码 | 分支条件、方法调用链、候选来源、历史逻辑线索 | 数据库物理结构、二代/当前项目等价逻辑、未经运行验证的 SQL |
| 访谈记录 | 业务口径、例外规则、人工确认结论 | 数据库类型、字段长度、真实码值全集，除非访谈明确给出 |

当多个证据冲突时，Agent 不得自行选择“看起来更合理”的值。必须记录冲突说明，并按优先级或用户确认结果处理。没有项目级证据优先级时，默认优先级为：数据库物理结构 > 当前项目 SQL/ETL > 发文/接口规范 > 当前业务代码 > 源文件样本 > 访谈记录 > 历史项目经验。

### 禁止写入元属性的内容

以下内容不得写入正式元属性，只能进入备注、整改、证据草稿或待确认：

1. 由英文名机器翻译得到的中文字段名或中文表名。
2. 由字段名猜测出的业务口径、码值说明、数据层级或载体类型。
3. 由历史项目、一代系统或相似表推断出的当前项目 Mapping SQL。
4. “通常是”“可能是”“应该是”这类不确定判断。
5. 为了让页面看起来完整而补齐的默认值。
6. 模板没有定义的属性、枚举值或动作类型。

如果用户明确要求先整理草稿，可以在草稿中保留推测，但必须标为 `待确认`，并写清推测依据；草稿不得被当作已发布模板校验通过的数据。

## Agent 操作流程

Agent 处理数据字典 / Mapping 任务前，应按下面流程：

1. 先读取本手册。
2. 确认用户操作的是哪个项目、哪个系统、哪个表、哪个场景。
3. 如果用户只描述规则，不直接改数据，先更新本手册。
4. 如果用户要求迁移或改数据，先读取现有表、字段、场景、Mapping 规则。
5. 按固定模版整理，不要改变业务含义。
6. 写入后检查：
   - 字段设计表能展示。
   - Mapping 场景 title 能切换。
   - 口径能展示。
   - 字段 Mapping 表有涉及字段和逻辑。
   - 长文本能通过悬浮框查看。

## 当前已确认的用户偏好

- 整体风格参考 Navicat，而不是纯黑、空旷、看不清的界面。
- 左侧菜单要窄、贴边、清晰。
- 数据字典重点是检索和关联搜索，性能要优先考虑。
- 字段设计中字段名和中文名要固定，其他列可以横向滚动。
- 字段类型要使用数据库类型，例如 `varchar`、`datetime`、`date`，不要每条记录各写各的。
- 码值说明要有固定 key-value 格式，方便悬浮框用表格展示。
- Mapping 要按场景 title 切换，不要所有场景堆在一起。
- Mapping 中「涉及字段」只放字段引用，「逻辑」才放加工规则。
- 长属性不要挤在表格里，要通过右下角悬浮框展开。
- 所有规则先沉淀成手册，再逐步固化为系统能力。
